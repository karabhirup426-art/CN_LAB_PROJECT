2. Why FTP Uses TCP Sockets (and not UDP)

  • 100% Data Integrity: File transfer cannot tolerate a single dropped, duplicated, or corrupted bit. TCP guarantees delivery through sequence numbers, acknowledgments (ACKs), and automatic retransmissions (ARQ).
  • In-Order Byte Delivery: TCP guarantees packets arrive in the exact order sent. UDP datagrams may arrive out-of-order, duplicated, or get dropped silently.
  • Flow and Congestion Control: TCP uses sliding-window flow control to prevent buffer overflow and adapts transmission rate dynamically based on network congestion.

3. Dual-Connection Architecture (Out-of-Band Signaling)

Unlike HTTP, standard FTP uses TWO separate TCP connections:

+------------------+                                      +------------------+
|    FTP CLIENT    |                                      |    FTP SERVER    |
+------------------+                                      +------------------+
        |                                                          |
        | ====== 1. Control Connection (Port 2121 - Persistent) ===|
        |        Commands: USER, PASS, PWD, PASV, RETR, STOR       |
        |        Replies : 220, 331, 230, 227, 150, 226            |
        |                                                          |
        | ====== 2. Data Connection (Dynamic Port - Ephemeral) ====|
        |        Transfers: Raw File Bytes or Directory Listing    |
        |        (Opens on demand, closes when transfer finishes)  |
        v                                                          v
  • 1. Control Connection (Port 2121 - Persistent): Stays open throughout the entire session. Carries small ASCII commands and 3-digit status codes. No file bytes ever travel over this connection.
  • 2. Data Connection (Dynamic - Ephemeral): Created on-demand exclusively for data-intensive transfers (file upload, file download, directory listing). Closed immediately once the transfer finishes (sending TCP FIN).

4. Passive Mode (PASV) vs Active Mode (PORT) & The Port Formula

  • Passive Mode (PASV - Recommended): The client asks the server to listen (PASV). The server opens an ephemeral TCP port and replies with 227 Entering Passive Mode (h1,h2,h3,h4,p1,p2). The client initiates the TCP connection. Highly firewall and NAT friendly.
  • Active Mode (PORT): The client opens a listening socket and instructs the server (PORT h1,h2,h3,h4,p1,p2) to connect back. Client-side firewalls and NAT routers almost always block this inbound connection.
Mathematical Port Encoding Formula (RFC 959):
Given (h1, h2, h3, h4, p1, p2), the IP address is h1.h2.h3.h4 and the Port is calculated as:
Port = (p1 × 256) + p2
Example: (127, 0, 0, 1, 193, 157) → (193 × 256) + 157 = 49408 + 157 = 49565.
Inverse (Server Decomposition): p1 = port // 256, p2 = port % 256.

5. Detailed Step-by-Step Code Walkthrough (Every Phase Explained)

Step 1: Server Startup & Listening

The server creates a welcoming socket, binds to IP 127.0.0.1 and Port 2121. It sets SO_REUSEADDR to prevent "Address already in use" errors when restarting, and sets a connection backlog of 10.

self.server_sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
self.server_sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
self.server_sock.bind((self.host, self.port))
self.server_sock.listen(10)

• AF_INET: Specifies IPv4 addressing.
• SOCK_STREAM: Specifies connection-oriented TCP byte stream.

Step 2: Multi-Client Connection & Concurrency

When a client connects, the main server loop accepts the connection and immediately hands it off to an independent worker thread (FTPServerSession). This ensures the server is non-blocking and handles dozens of concurrent clients simultaneously across different terminal tabs.

client_sock, client_addr = self.server_sock.accept()
session = FTPServerSession(client_sock, client_addr, root_dir, users_db)
session.start()  # Spawns a dedicated thread!

Step 3: Initial Greeting Code (220)

As soon as the TCP 3-way handshake finishes, the server sends the standard RFC 959 greeting over the control connection: 220 Welcome to CN Lab Python Socket FTP Server (RFC 959)\r\n.

Step 4: Authentication Handshake (USER & PASS)

1. Client sends: USER student\r\n
2. Server responds: 331 User name student okay, password required.\r\n
3. Client sends: PASS cnlab2026\r\n
4. Server validates credentials against the database:
   • If invalid → replies 530 Authentication failed.
   • If valid → sets is_authenticated = True and replies 230 User logged in successfully.

Step 5: Directory Operations & Security Sandboxing (PWD, CWD)

The server tracks the virtual directory relative to root (e.g. /). When the client issues PWD, it replies with 257 "/" is the current directory. For CWD, the server converts the virtual path to a canonical absolute path and strictly validates that it cannot escape the storage root (preventing directory traversal attacks like ../../etc/passwd).

abs_path = os.path.abspath(os.path.join(self.root_dir, target))
if not abs_path.startswith(self.root_dir):
    self.send_response(550, "Access Denied: Path escapes sandbox!")
    return None

Step 6: The Passive Mode Dance (PASV)

Before any transfer, the client sends PASV. The server binds an ephemeral listener socket to port 0, which tells the operating system kernel to allocate an unused high-numbered port. The server reads the assigned port via getsockname()[1], calculates (p1, p2), and returns 227 Entering Passive Mode (127,0,0,1,p1,p2). The client connects its data socket to that address.

Step 7: Directory Listing (LIST)

Client sends LIST. The server sends 150 Here comes the directory listing, inspects files in the directory, formats each entry matching standard Unix ls -l format (permissions, size, date, filename), streams those bytes across the data socket, closes the data socket, and sends 226 Directory send OK on the control socket.

Step 8: File Upload (STOR) & The TCP FIN Mechanism

Client sends STOR report.pdf. Server replies 150 Ok to send data. Client reads the local file in 8192-byte chunks and sends them across the data socket. When the client finishes writing the file, it calls data_sock.close(). In TCP, closing a socket transmits a FIN packet. On the server side, recv(8192) returns 0 bytes (empty string b''), signaling End-Of-File (EOF). Server writes the final chunk, closes the file, and sends 226 Transfer complete.

Step 9: File Download (RETR) & Throughput Calculation

Client sends RETR report.pdf. Server validates the file exists, gets size via os.path.getsize, and replies 150 Opening BINARY mode data connection. Server reads the file in 8192-byte chunks, streams over data socket, and closes the socket. Client reads until EOF, records elapsed time, calculates throughput in KB/s, and receives 226 Transfer complete.

Step 10: Graceful Disconnect (QUIT)

Client sends QUIT. Server responds 221 Goodbye! Closing control connection. Both client and server close their control sockets cleanly, releasing system resources.

8. Is It Simulation-Based?

  • FTP (Basket 3): 100% Real OS Sockets. Operates on real operating system TCP sockets (SOCK_STREAM), performs real 3-way handshakes, transfers real binary documents, and verifies 100% data integrity with MD5 checksums.
  • DNS (Basket 2): 100% Real OS Sockets. Real UDP datagrams (SOCK_DGRAM) packing binary RFC 1035 wire packets. Responds to native nslookup and forwards queries to Google DNS (8.8.8.8).
  • ARP (Basket 1): Real Packets over a Simulated Switch. The 42-byte RFC 826 packet (14-byte Ethernet + 28-byte ARP) is authentic binary packed via struct. The switch is simulated over UDP because raw Layer-2 Ethernet sockets require sudo/root privileges on macOS and Windows.

10. The Unified 3-Tier End-to-End Story

  1. Tier 1: DNS (Infrastructure): Client wants to connect to ftp.cse.myuniv.edu. It asks our authoritative DNS server (dns_server.py), which resolves ftp.cse.myuniv.edu → 192.168.151.5.
  2. Tier 2: ARP (Data Link): To send IP packets to 192.168.151.5 on the local network, host broadcasts: "Who has 192.168.151.5?". The switch floods it, the target answers with its MAC, and the host updates its ARP cache.
  3. Tier 3: FTP (Application): With MAC and IP resolved, client initiates a reliable TCP connection on port 2121 to our FTP server (ftp_server.py), authenticates, opens a passive data channel (PASV), and transfers files with 100% data integrity verified by MD5 hashes.

11. Top Lab Viva Questions & Answers

Q1: What is out-of-band signaling in FTP?
FTP uses two separate connections: a persistent Control Connection (port 2121) for commands and replies, and a temporary Data Connection negotiated on-demand for transferring file bytes or directory listings. This allows commands (like aborting a transfer) to be sent without corrupting the file stream.
Q2: Why is TCP used for FTP instead of UDP?
File transfer cannot tolerate a single dropped, duplicated, or reordered bit. TCP provides guaranteed delivery, sequencing, acknowledgments (ACKs), automatic retransmissions, and sliding-window flow control. UDP provides none of these guarantees.
Q3: Explain Passive Mode (PASV) vs Active Mode (PORT).
In Active Mode (PORT), the client opens a data port and asks the server to connect back to it, which is almost always blocked by client-side firewalls and NAT routers. In Passive Mode (PASV), the server opens a temporary high port and the client initiates the connection to the server, which traverses firewalls smoothly.
Q4: How does the server know when an uploaded file is complete without an EOF character?
When the sender finishes writing all file bytes, it closes the data socket (data_sock.close()). In TCP, closing a socket sends a FIN packet. On the receiving side, recv() returns 0 bytes (empty string b''), which signals End-Of-File (EOF).
Q5: How do you calculate the port number from (h1, h2, h3, h4, p1, p2)?
The IP is h1.h2.h3.h4. The port is computed as: Port = (p1 × 256) + p2. For example, (193, 157) gives (193 × 256) + 157 = 49565.
Q6: What is directory traversal and how does your server prevent it?
Directory traversal (e.g. CWD ../../) is an attack where a user attempts to navigate out of the root folder to access sensitive host files. Our server normalizes all requested paths with os.path.abspath and verifies that the canonical path starts with self.root_dir, returning 550 Access Denied if it escapes.
Q7: How did you verify data integrity across the socket?
We compute the MD5 cryptographic checksum of the local file before uploading and compare it with the MD5 checksum of the downloaded file. Both hashes match byte-for-byte, verifying 100% loss-free transmission over TCP.
Q8: Why does DNS use UDP while FTP uses TCP?
DNS queries and replies are small (under 512 bytes), so establishing a TCP 3-way handshake would double the lookup latency. Hence, DNS uses UDP for speed. FTP transfers large binary files requiring reliability, so it must use TCP.
Q9: What is Gratuitous ARP?
A host broadcasting an ARP packet announcing its own IP (sender IP = target IP). It allows other hosts to update their ARP tables and detects duplicate IP address conflicts on the network.
